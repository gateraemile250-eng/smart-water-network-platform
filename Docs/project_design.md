# Smart Water Network Intelligence Platform

## Phase 1: Project Design

### 1. Business and Operational Problem

Water distribution utilities operate networks consisting of pipes, pumps, valves, reservoirs, and other infrastructure that must continuously deliver water to customers.

Modern water networks can use pressure, flow, reservoir-level, and other sensors to monitor network conditions. These sensors can generate continuous streams of measurements. However, raw sensor readings alone do not provide enough information for engineers and operators to quickly understand when abnormal network behaviour is occurring.

Abnormal conditions such as unusually high flow combined with sustained pressure reduction may indicate a possible water leak or another network problem. If these patterns are not identified and investigated in a timely manner, they may contribute to water losses, operational inefficiencies, and delayed maintenance response.

The Smart Water Network Intelligence Platform will simulate and process continuous water-network sensor data, validate incoming readings, identify abnormal pressure and flow patterns that may indicate potential leaks, associate detected events with geographic and network information, and provide operational and historical analytics.

The platform is intended to support engineers, network operators, maintenance teams, and managers in investigating network conditions and making better-informed operational and maintenance decisions.

### Why This Problem Requires a Data Engineering Solution

The challenge is not simply collecting sensor readings. A useful monitoring system must be able to:

- continuously ingest sensor events;
- validate incoming data and isolate invalid records;
- process large volumes of time-series measurements;
- detect sustained abnormal behaviour rather than reacting to individual readings;
- combine sensor data with network and geographic information;
- store historical data for later analysis;
- generate potential leak alerts;
- provide reliable data for dashboards, GIS analysis, and machine-learning models;
- monitor the reliability of the data pipeline itself.

Therefore, the project requires a data platform that can support both real-time stream processing and historical batch analytics.
### 2. Client and System Users

#### Target Client

The platform is designed as an independent portfolio project for a water utility responsible for operating and maintaining a water-distribution network.

#### System Users

- **Network Operators:** Monitor sensor readings, network conditions, and active alerts.
- **Water Engineers:** Analyze pressure, flow, abnormal behaviour, and historical network performance.
- **Maintenance Teams:** Investigate potential leaks and identify affected network assets.
- **GIS/Asset Teams:** Connect incidents with pipes, valves, sensors, reservoirs, and geographic areas.
- **Management:** Monitor higher-level indicators such as incident frequency, water-loss trends, detection time, and maintenance performance.

Different users require different outputs: operational teams need timely alerts and network conditions, while engineering and management users need historical analysis and aggregated indicators.

### 3. Decisions the System Should Support

The platform should provide reliable information that helps users:

- identify abnormal pressure and flow behaviour that may require investigation;
- determine the network location and nearby assets associated with a potential incident;
- prioritize potential incidents based on severity and persistence;
- analyze recurring abnormal conditions and historical leak patterns;
- monitor network and maintenance performance over time.

The platform provides decision-support information; detected anomalies are treated as potential incidents requiring investigation rather than automatically confirmed leaks.

### 4. Sensor Event Design

The platform will process time-series events representing measurements generated by water-network sensors.

At minimum, a sensor event will contain:

- a unique event identifier;
- event timestamp;
- sensor identifier;
- sensor type;
- measured value;
- measurement unit.

Sensor location and network information will be maintained separately as sensor/asset metadata and can be joined with events when geographic or network context is required.

The final event schema will be refined after inspecting the BattLeDIM dataset in Phase 2.

### 5. System Outputs

The platform will produce four main types of outputs:

- **Validated sensor readings:** Clean sensor events that pass data-quality checks.
- **Rejected events:** Invalid or malformed events retained for investigation and pipeline monitoring.
- **Potential leak/anomaly alerts:** Alerts generated when sustained abnormal network behaviour meets defined detection criteria.
- **Analytical metrics:** Aggregated historical and operational measures used for trend analysis, dashboards, GIS analysis, and later machine-learning workflows.

These outputs will support operational monitoring, incident investigation, historical analysis, and management reporting.

### 6. Leak-Detection Concept

The platform will initially identify potential leaks using sustained abnormal patterns in sensor measurements, particularly changes in pressure and flow.

A single abnormal reading will not automatically be treated as a leak. Detection will consider whether abnormal behaviour persists over a defined period and differs from expected network behaviour.

The first implementation will use a rule-based detection baseline. Machine-learning methods may later be introduced and compared with this baseline.

Detected conditions will be classified as potential incidents requiring investigation rather than automatically confirmed leaks.

Exact detection thresholds and rules will be defined after the BattLeDIM data is explored and understood.

### 7. Requirements and Technology Mapping

Technology choices are based on system requirements rather than adding tools unnecessarily.

| Requirement | Technology |
|---|---|
| Simulate continuous sensor readings | Python |
| Transport streaming events | Apache Kafka |
| Validate and process streaming data | Spark Structured Streaming |
| Store structured and spatial network data | PostgreSQL/PostGIS |
| Store historical analytical datasets | Parquet data lake |
| Orchestrate scheduled batch workflows | Apache Airflow |
| Provide dashboards and spatial analysis | Power BI and GIS |
| Reproduce the local platform | Docker |
| Extend selected components to the cloud | AWS |

MongoDB, Hadoop, and machine learning will be evaluated in later phases and included only where they provide a clear technical or learning purpose.

### 8. Initial System Architecture

The initial platform will follow this data flow:

Historical water-network data → Python sensor simulator → Kafka → Spark Structured Streaming → validated/processed data → PostgreSQL/PostGIS and Parquet data lake → dashboards and GIS analysis.

The streaming pipeline will handle continuous sensor processing and potential anomaly detection. Airflow will later orchestrate scheduled batch workflows.

Selected components may later be extended to AWS after the local pipeline is working and validated.
